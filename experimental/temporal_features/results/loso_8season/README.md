# Leave-one-season-out validation of the temporal satellite-feature experiment

**Experimental. Nothing in this directory feeds production.** The shipped model
(`ml-service/app/model.pkl`), its training data
(`ml-service/data/training_data_real.csv`), the crop registry
(`ml-service/data/crops.csv`), the database and every prediction endpoint were
read but never written.

Generated by `experimental/temporal_features/run_loso.py`.

```bash
cd ml-service
PYTHONPATH=. python -u ../experimental/temporal_features/run_loso.py
```

## What was tested

The temporal-feature experiment had been validated on **one** fixed holdout —
2021-22 plus 2022-23. A single split cannot distinguish a real per-crop gain
from an artifact of which two seasons happened to be held out, and several
crops carried only 28–68 holdout rows. This re-validates the same experiment
across **all 8 Sentinel-2 seasons**, so every crop gets 8 independent
estimates instead of 1.

No new satellite data was fetched. No feature engineering was rewritten. The
existing implementation is reused wholesale; the only new code is the fold
loop and the per-crop bookkeeping.

## How LOSO validation works here

Eight folds. Each holds out exactly one season, trains on the other seven, and
is scored only on the held-out season.

```
fold 1   test 2017-18   train 2018-19 … 2024-25    2056 / 322
fold 2   test 2018-19   train all except 2018-19   2021 / 357
fold 3   test 2019-20   …                          2039 / 339
fold 4   test 2020-21   …                          2093 / 285
fold 5   test 2021-22   …                          2095 / 283
fold 6   test 2022-23   …                          2100 / 278
fold 7   test 2023-24   …                          2112 / 266
fold 8   test 2024-25   train 2017-18 … 2023-24    2130 / 248
```

2015-16 and 2016-17 exist in the PBS sources but are **not** included, and
could not be: Sentinel-2 L2A begins 2017-03-28, so a rabi window ending before
that has no imagery at all. Inventing those seasons was not an option.

A crop-season is scored only when the held-out season holds at least 5 rows for
that crop and the true yields actually vary. Three folds fail that test and are
recorded in `validation_audit.json` under `insufficient_data_folds` rather than
being quietly dropped: onion 2017-18 (0 rows), maize 2020-21 (0 rows), maize
2024-25 (0 rows). Both crops have genuine gaps in the source data — onion
covers 7 seasons, maize 6.

## Models compared

All three arms use identical rows, identical labels, identical folds and
identical forest hyper-parameters (`n_estimators=500`, `max_depth=25`,
`criterion="squared_error"`, `random_state=42`). **The feature set is the only
thing that varies.**

| Arm | Feature group | Columns after `_isna` flags + crop one-hot |
|---|---|---|
| `current` | the 5 season-median composite indices (`prod_ndvi`, `prod_evi`, `prod_ndwi`, `prod_savi`, `prod_nbr`) | 21 |
| `temporal` | all 100 engineered temporal + coverage/quality columns | 211 |
| `veg_only` | the 90 vegetation columns, with the 10 coverage/quality columns removed | 191 |

### Why `current` is a refit and not the shipped artifact

`app/model.pkl` was trained on one fixed split, so it cannot be
cross-validated — scoring it on 2018-19 would be scoring it on its own
training data. The `current` arm therefore **refits the production feature
group** on each fold. That makes the comparison controlled: same rows, same
hyper-parameters, features the only difference.

Two consequences to keep in mind:

- The `current` numbers here are **not** the shipped model's numbers. They are
  what the production *feature design* achieves under LOSO.
- The shipped model covers 10 crops; **barley was removed from production** in
  an earlier step because its observation window is byte-identical to wheat's.
  All three arms here include barley so the comparison stays symmetrical, but
  barley's production column does not exist in the live model. Its rows here
  describe a hypothetical, not the shipped system.

### Why `veg_only` exists

`valid_px_mean` — the mean pixel count in a district reduction — is effectively
the district's **area**, and it takes a distinct value in all 34 districts. A
forest can use it as a district lookup, which inflates apparent skill without
reading any vegetation. `veg_only` drops the whole coverage/quality block so
that any gain it still shows is attributable to vegetation signal.

## Feature groups, as actually implemented

Built by `ml-service/scripts/build_temporal_features.py` from per-date district
observations. Per index (NDVI, EVI, NDWI, SAVI, NBR) — 19 columns each:

- **Level** — `_season_median`, `_early_mean`, `_mid_mean`, `_late_mean`,
  `_q1_mean` … `_q5_mean`, `_peak`, `_min`
- **Shape** — `_amplitude`, `_early_to_mid`, `_mid_to_late`, `_overall_change`
- **Growth** — `_growth_slope`, `_decline_slope`, split at the peak
  *observation* rather than a calendar midpoint, expressed per day because
  observations are unevenly spaced
- **Timing** — `_peak_frac`, the peak's position as a fraction of the window

Coverage/quality — 10 columns: `valid_observation_count`,
`early/mid/late_observation_count`, `segments_covered`, `cloud_pct_mean`,
`valid_px_mean`, `first_obs_doy_frac`, `last_obs_doy_frac`, `max_gap_days`.

**Not present, despite appearing on the candidate list:**

- **No per-index standard deviation.** Dispersion is represented by
  `_amplitude` (peak − min) only.
- **No radar.** `fetch_temporal_observations.py` reads
  `COPERNICUS/S2_SR_HARMONIZED` only. There are **no VV/VH features** in this
  experiment, even though `app/field.py` can fetch Sentinel-1 for the per-farm
  path.

## Leakage prevention

| Requirement | How it is met |
|---|---|
| Held-out season contributes nothing to training | Asserted per fold; `held_out_rows_found_in_training = 0` for all 8 |
| Preprocessing never sees held-out targets | The only preprocessing is median imputation, and it never reads `y` |
| Imputation fitted on training seasons only | `impute(Xtr, Xte)` takes `np.nanmedian(Xtr, axis=0)` and applies it to both halves |
| Scaling fitted on training only | No scaling exists — a random forest is scale invariant |
| Feature selection fitted on training only | No feature selection exists |
| Hyperparameters not tuned on the held-out season | `RF_KWARGS` is a fixed constant; nothing is searched |
| No global statistic computed before the split | Verified by recomputation, below |
| No future-season yield information | Features never read `actual_yield`; the label is copied through only |
| Observations stay inside the correct crop-season window | 0 of 136,687 observations fall outside their own `(crop, season)` window |
| No held-out observation reaches training | No two seasons of one crop share a calendar date, so no observation can serve two rows |

The **recomputation check** is the concrete form of "no global statistic before
the split": 60 rows spread across the dataset had their features rebuilt from
strictly their own `(crop, season, district)` observations and compared value by
value with the stored CSV. **0 differing values.** If anything had been pooled
across seasons, these would disagree.

The crop one-hot is built from the **training** seasons' crops each fold, not
from the full dataset.

## Limitations

1. **The dataset is district-level, reduced at 500 m.** Every row is a mean
   over a whole district (~5,000 km²). This validates the temporal feature
   *concept* at district-level scale; it does **not** prove the approach works
   on the production farm-level field geometry, which is a 10 m circle sized
   from `area_hectares`.
2. **`current` is a refit**, not the shipped model. See above.
3. **Barley is not in the production model.** Its rows here are hypothetical.
4. **Three crop-season folds are unscored** for lack of data.
5. **Slope features are 8–9% missing** — a slope needs at least 3 observations
   on the relevant side of the peak, and a cloudy season sometimes lacks them.
   Only 40 of 100 engineered columns are fully populated.
6. **One split per season, one seed.** LOSO gives 8 estimates per crop, which
   is far better than 1, but the fold-to-fold standard deviations are large
   (see `crop_summary.csv`) and no confidence intervals are computed.
7. **Overall pooled R² is not a meaningful headline.** Crop yields span 0.8 to
   63 t/ha, so a pooled figure mostly measures the between-crop scale gap.
   `crop_summary.csv` is the result; the macro average is secondary.

## Interpreting the results

Read `crop_summary.csv` first, per crop, and read `std_r2` alongside
`mean_r2` — several crops swing by more than a whole unit of R² between folds,
which means a single-split result for them was not informative.

A negative R² means the model did worse on that fold than predicting the
held-out season's own mean. Many crop-seasons are negative for **all three**
arms, which is a statement about the labels and the district-average
representation, not about temporal features specifically.
